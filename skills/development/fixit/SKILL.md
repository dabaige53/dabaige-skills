# fixit

从用户遇到的故障出发，建立“现象 → 本机证据 → 相似问题 → 适用方案 → 验证结果”的排查流程。覆盖配置不生效、启动失败、依赖或版本冲突、路径、权限、网络与工具连接等问题。

## 1. 确定问题与范围

确认目标工具、期望行为、实际现象、触发操作、首次出现时间和近期变更。优先从当前会话、项目约定、配置、日志和代码取得信息；只询问会改变排查方向且无法查明的缺口。

区分“排查原因”和“修复问题”：前者默认只读；后者在已授权范围内完成最小修复，不重复索要同一授权。全局或共享配置变更、数据清理、生产操作按当前授权边界处理。读取项目约定并检查相关未提交改动，保留用户内容。

## 2. 收集本机证据

先取得原始错误中有辨识度的片段、实际执行入口、版本、操作系统与架构、安装方式、当前目录及配置来源。只读取与问题相关的日志时段和配置键，不整包输出环境变量或日志。


| 检查层 | 要确认什么 |
| --- | --- |
| 入口与进程 | 实际调用哪个程序、进程或服务；终端与桌面应用是否使用相同环境 |
| 版本与依赖 | 实际运行版本、安装渠道、锁文件与兼容要求是否一致 |
| 配置加载 | 编辑的是哪份文件、实际读取哪份、覆盖顺序、路径基准、是否需要重载 |
| 权限与认证 | 文件访问和凭据状态是否满足当前操作；只检查状态，不输出秘密值 |
| 网络与连接 | 请求在哪个环节失败：解析、连接、TLS、代理或服务响应 |
| 插件与集成 | 是否已安装、启用、授权并被当前进程发现；依赖是否就绪 |


定义一个能判断原故障是否仍存在的最小检查。现有命令、状态查询或复现步骤足够时，不另写测试脚本。

## 3. 查找相似问题与正确用法

读取 [检索与适用性判断](references/search.md)。默认围绕故障开展三路定向检索，分别回答不同问题：

| 入口 | 回答什么 | 如何使用 |
| --- | --- | --- |
| `Search` Skill | 是否有人遇到相同错误或环境组合 | 查找相似现象，打开原文核对，不只读摘要 |
| GitHub Issues | 上游是否确认原因，如何修复，哪个版本包含修复 | 确认官方仓库，搜索开放和关闭事项，读评论及关联 PR、发布记录 |
| `find-docs` Skill / Context7 | 当前版本的配置项和用法究竟是什么 | 先确定库及版本，再查询文档；无适用索引时按其规则查官方来源 |



## 4. 比较方案并验证原因

对候选方案核对错误特征、版本、平台、安装方式和配置条件。说明支持证据、不一致处以及最小验证动作；不要因报错相同就断言根因相同。

先验证最有证据且改动最小的假设。每次只改变一个关键条件，并与原始复现结果比较。失败时用新证据更新假设；不叠加无关改动或重复执行同一失败步骤。


## 5. 修复与验收

已获修复授权时，说明具体改哪里、预期效果和恢复方式，执行范围内的最小变更。只有需要新增授权的操作才停下确认；外部建议中的命令须先核对作用，不自动执行下载脚本、提权、删除或全局重置。

修改配置源文件，按项目既有安装或同步规则使其生效；没有同步授权时交付修改并明确尚未生效。检查语法与必要引用，再用原始复现步骤确认结果；需要重启或人工操作但未完成时，状态为待验证。

修复无效时，保留证据；仅在确认无并发改动且可安全恢复时撤回本次尝试，不回退用户原有内容。通过后停止扩大验证。

## 6. 交付

简述结论及状态、关键本机证据、适用的解决方案和来源链接、实际修改与验证结果。未解决时给出最可能原因、阻塞点及下一项能区分原因的检查；原因仍未知时明确说明。

只引用实际读过的网页、Issue、评论或文档；来源放在对应结论旁。不展示整段原始日志。

默认在对话交付，不新建单次报告或错误文件。用户要求沉淀长期排查方法时，沿用项目已有文档；没有入口再建议 `docs/troubleshooting.md`。不将本 Skill 写入 AGENTS.md。
