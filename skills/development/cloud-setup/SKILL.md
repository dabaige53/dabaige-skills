# cloud-setup

各端可以分工，但业务数据、任务状态和产物使用项目约定的共同来源。

## 配置与优化

1. 新项目根据工作内容确定各子项目的运行位置、依赖和产物；已有项目读取现有配置、启动入口和运行记录。两者都标记必须本地运行或逐端配置的内容。
2. 沿用现有配置方式：公共设置统一维护，节点只保留路径、运行身份和资源额度等差异。查清配置文件、环境变量和启动参数的覆盖顺序。
3. 修改实际生效的配置，接好运行依赖、共享资源、服务调度和产物访问。凭据沿用项目管理方式，通过变量或挂载提供。
4. 针对实际问题调整构建复用、调度周期、并发、超时、重试和缓存。具体方法见 [配置优化](references/configuration.md)。
5. 按授权使配置生效，用受影响的实际入口确认结果。失败时参考 [问题定位](references/runtime-checks.md)。重启、部署和业务写入沿用当前授权。

已有信息由 Agent 自行查明，在当前授权内能完成的配置直接完成。缺少密钥、权限或必须由人操作时，继续完成其他配置，最后集中列出用户需要补充的事项；每项写清需要什么、用在哪里、如何提供。密钥通过项目既有凭据入口保存。只要求方案时交付方案。

## 旧项目迁移

涉及历史项目迁移或多端统一时，使用 [迁移与重点检查清单](references/migration-checklist.md)，按子项目梳理现状、目标与本地例外，再分批调整和切换。

## 交付

新项目构建、旧项目迁移和后续配置调整，都必须逐个子项目说明哪些内容需要本地运行、哪些需要在指定节点配置，以及原因、操作入口和重点检查项。明确“本地”指哪台机器；没有本地要求时也写明。

说明改了什么、是否生效、以后如何运行。格式参考 [结果说明](references/reporting.md)。迁移清单和本地要求保存到项目已有运行文档；新增文档放在根目录 `docs/`。
