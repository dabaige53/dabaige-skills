# Git 操作

只保留三个入口。用户说“git 分支整理”“git 提交”或“git 同步”时，直接执行对应流程，不扩展成其他操作。

## 1. `git 分支整理`

运行 `scripts/branch-cleanup.py`。先查看预览，再用 `--apply` 执行。

- 先确认当前仓库、当前分支和工作区状态；有未提交改动时停止，不切换分支、不暂存、不覆盖现场。
- 执行时先 `git fetch --prune`，再尝试将当前分支从其已配置的 upstream **仅快进**到最新状态。
- 以远端默认分支为清理基准；只清理已确认是基准分支祖先的本地分支。
- 保留当前分支、默认分支、常见长期分支、其他 worktree 正在使用的分支，以及任何未合并或无法判断的分支。
- 删除前为分支创建 `refs/backup/git-ops/` 恢复引用；只删除本地分支，不删除 GitHub 上的远端分支。
- 不自动合并其他功能分支。只快进当前分支的 upstream；若分支已分叉或快进失败，停止并报告，不擅自 rebase 或创建 merge commit。

## 2. `git 提交`

运行 `scripts/commit-check.py` 检查，再由 Agent 阅读实际差异并完成提交。

1. 用户点名文件、目录或某个 Skill 时，将范围解析为仓库根目录下的实际路径。以下命令都在仓库根目录运行，使用同一组路径，每个路径作为单独参数传入。
2. 用 `commit-check.py -- <路径…>` 检查范围内的改动，阅读差异，并用 `git --literal-pathspecs add -A -- <路径…>` 暂存范围内的新增、修改和删除。
3. 运行 `commit-check.py --staged-only -- <路径…>`，核对暂存差异。用 `git --literal-pathspecs commit --only -m "提交说明" -- <路径…>` 提交，保留范围外已暂存的内容。若只授权文件中的部分改动，按获准的差异块准备提交。
4. 未限定路径时沿用全仓检查；确认改动都属于本次提交后，再使用 `git add -A`、暂存检查和普通提交。没有待提交内容就结束。提交后按用户要求决定是否同步。

用户明确给出提交说明时优先使用；否则按实际改动生成简洁、准确的提交说明。

## 3. `git 同步`

运行 `scripts/sync-check.py`，通过后按顺序执行：

1. 确认工作区干净、当前分支有已配置的 upstream，且没有进行中的 merge/rebase/cherry-pick。
2. `git fetch --prune`。
3. 再运行 `sync-check.py` 检查远端更新和本地领先/落后情况。
4. 执行 `git rebase @{upstream}`，将本地提交放到远端最新提交之后。
5. rebase 成功后执行普通 `git push`。

遇到冲突、权限错误、非快进推送被拒或远端状态变化时，立即停止，保留当前分支和 rebase 现场，向用户报告原因。

## 通用边界

- 只操作用户当前指定或当前工作目录对应的仓库；仓库不明确时先询问。
- 不执行 `git reset --hard`、`git clean -fd`、`git push --force`，不删除远端分支。
- 脚本默认只检查或预览；只有对应流程明确要求执行时才传 `--apply`。
- 所有结果如实报告：完成了什么、保留了什么、失败在哪里。不得把未执行的检查说成已通过。
