# 开发项目规范

## 1. 确定范围与完成条件

读取项目约定、现有入口、配置和工作区差异。明确目标项目、用户流程、数据输入、输出及已授权操作；用户提供聊天引用时先读取对应聊天，采用后续修正后的要求。保留已有设计、未提交修改和明确保留的数据来源。

将需求对应到实际文件与行为：项目资料是否齐全、运行入口是否读取配置、数据源是否正确、性能问题是否有证据。先完成可独立处理的内容；只有无法从本地代码、配置、元数据及所引聊天确认的关键缺口才询问。

## 2. 补齐项目基础文件

在每个独立运行的项目根目录维护以下内容；复用既有文件名和配置格式，不另建重复配置系统。

| 文件 | 必须承载的内容 |
| --- | --- |
| `AGENTS.md` | 项目背景、架构边界、开发规范、AI 工作要求及按需文档入口；修改时采用 writing-for-agents |
| `.env` | 本项目环境变量和敏感配置的读取入口，加入版本控制忽略规则；沿用已有文件或挂载方式 |
| `.env.example` | 变量名和无敏感信息的示例，便于初始化 |
| 配置文件 | 数据源映射、文件路径、运行参数、业务选项；沿用现有格式，例如 `config/runtime.toml` |
| 根目录执行脚本 | 统一启动或执行入口，定位项目目录，加载配置与 `.env`，将变量传入运行进程 |
| `README.md` | 项目用途、准备条件、运行命令、配置位置、输出位置和必要的故障入口 |

配置要贯通到实际执行路径。确定并记录参数覆盖顺序，避免文档、预检查和业务脚本各读不同路径。常规启动复用有效构建；保留源码变化后的重建方式。检查从其他工作目录调用入口也能定位项目文件。

沿用项目已有的环境变量管理方式，按项目和环境隔离敏感配置。检查只输出变量名和状态，不输出密钥值，不将密钥写入代码、日志或文档。保留已挂载的 `.env`，避免覆盖；缺少变量时明确报告，不将示例值当作有效配置。

完成条件：文件存在且内容与当前项目一致；入口实际使用配置；运行进程能读取所需环境变量，缺失变量时给出明确错误。

## 3. 按数据血缘调整来源

涉及切源或代码迁移时，读取 [数据源调整规则](references/data-sources.md)。列出每个业务输入的当前来源、目标来源、加工步骤、消费模块与验证方式。

对已确认迁移的数据源修改实际读取代码和配置。保留用户明确指定的例外及未迁移文件。找不到旧表名时，继续追踪原始数据到派生结果的加工代码；搬迁功能时检查依赖模块、SQL、模板和参考文件是否齐全。

完成条件：每个受影响输入均已确认来源，或有具体缺口记录；查询和计算保持既有统计口径。离线等价、真实只读连通和完整业务运行分别报告，不能互相替代。

## 4. 依据证据优化处理效率

涉及性能时，读取 [性能优化与验收](references/performance.md)。先记录可复现的输入规模、耗时或重复工作量，再优先修复影响用户流程最大的瓶颈。选择最小改动，保持结果、顺序、异常行为及恢复能力。

完成条件：相同输入下业务结果等价，且目标耗时、查询次数、处理范围或资源上限有可检查的改善；未实测的收益仅列为待验证。

## 5. 验证与交付

按变更选择一次覆盖本轮范围的最小跑通检查：配置解析、入口运行、相关回归、SQL 结果对照及必要的构建或类型检查。仅在失败、追加修改或仍有具体风险时补查；异步检查未返回结果时标为待完成。

缺失文件、未确认映射或运行阻塞写入对应项目 `error.md`：日期、失败步骤、缺失项、证据位置、影响范围、下一步和解决状态。保留已有记录，解决后更新状态；不写入密钥，不以记录错误替代可完成的修复。

交付说明实际改动、验证证据、尚未完成项及配置位置。性能数据标明合成或真实输入；完整业务执行、生产写入和部署各自按授权与实际结果报告。
