# Readable Text

让读者快速找到重点，准确理解内容，并能比较同类条目。可读性不是字数越少越好；保留会影响判断与行动的信息。

## 确定本次写作方式

沿用用户已给出的读者、用途、语言、语气、长度和交付格式。信息足够就直接处理；只有缺失内容会改变结论或写作方向时才问关键问题。未指定语言时跟随用户和原稿，不强制翻译。

- **新写**：从材料中提取事实、读者要知道的结论及下一步行动，再组织成文。不要为凑模板编造日期、状态、数字或引文。
- **优化**：先辨认原稿主旨和必须保留的事实、条件与语气，再调整顺序、句子和术语。只要求校对时不重构全文；只要求建议时不覆盖原稿。
- **批量**：先确定读者要比较什么，把同类条目放在一起，选定共同字段、顺序、术语和状态表达，再整组生成或修改。不能只逐条润色而不比较相邻条目。

## 五条表达原则

### 1. 按读者容易理解的顺序写

优先让读者尽早看清“谁做什么”或“什么发生了变化”。共同主体明确时可省略主体，以动作开头；主体不同或责任重要时保留主体。把空泛名词改为具体动作，例如“进行方案的优化工作”改为“优化方案”。

英文通常优先使用主语、动词、宾语的顺序。中文按自然语序表达，不机械套用英文规则；重要条件可先写，如“付款失败时，系统保留购物车”。不要为了主动句臆造执行者。

### 2. 把区分条目的信息前置

先判断读者是要找对象、看状态、了解结果，还是决定下一步行动，再把对应关键词放在开头。删除“关于”“本条信息主要介绍”等没有区分作用的开场。

状态用于分流时可写“已发货：订单 1001”；按对象查找时可写“订单 1001：已发货”。重点前置优先于统一动词开头，不要把所有标题改成同一个空泛动作。真实对象名、关键词不能为了短而丢失。

段落开头先给该段要点，再解释原因、证据或行动；需要铺垫的叙事按其用途处理。

### 3. 同类内容使用同一结构和词汇

同一组可比较条目采用一致的字段和顺序，例如“问题 + 影响”或“结论 + 依据”。不同内容类型可分别分组，不强塞进一个模板。

同一概念使用同一名称，优先沿用原稿或项目术语。不要为避免重复而把同一个 GitHub issue 交替称为“问题”“页面”“工单”。也不要把原本不同的概念合并，如订单金额与实收金额。

统一的是阅读方式，不是强制每句同样长、每段同样多句；长文只在并列部分采用平行结构。

### 4. 让表达差异对应真实差异

同类摘要保持相近的信息层级。不要有的只写结论，有的突然加入版本、地区、单个例子或长篇过程，让读者误以为这些差异代表重要程度。

有意义的差异要保留，并说明意义。版本限定的故障必须保留版本；缺少统计不等于数量为零；有些项目缺字段时不要编造补齐。必要时改用更合适的分组或说明缺失情况。

用明确的数量、范围或优先级表达重要程度，不用篇幅和形容词暗示。只有原材料有数据时才给出数量、比例或排序；多个主题可重叠时不要暗示它们互斥。精简详情时，保留影响判断的条件；只有确有详情入口时才提示读者查看。

### 5. 让动词准确表达内容性质

让读者从动词看出是在描述问题、认可、请求、决定还是行动。例如“反馈登录失败”“认可离线功能”“请求批量导出”。按真实材料和读者场景选词，不按看板目的强行改变材料立场。

不要把中性反馈升级为“痛斥”或“热爱”，不要把计划写成成果。正负混合内容可写“认可新功能，但反馈操作步骤过多”，不能为了统一情绪只保留一边。客观报告用中性动词，建议与事实分开。

## 成稿与一次通读

按用户要求交付可直接使用的成稿。默认不给长篇修改过程；用户要求对照或解释时，再附关键改动与理由，和正文分开。文件、表格或结构化输入保留必要的 ID、对应关系与字段，不擅自排序或合并条目。

交付前通读一次，按以下问题修正实际问题，不为每项输出评分：

- 只读标题、条目开头和段落首句，能否找到重点并区分条目？
- 同组内容的结构、状态和术语是否一致？必要差异是否清楚？
- 删除的内容是否确属重复或无关，而不是读者判断与行动所需的细节？
