# 迁移方式与验证

先确认当前 CLI 的 `op run --help`、`op inject --help` 和条目模板，再选项目实际支持的方式。

## 环境变量

在仓库外的本机私有引用文件中保留变量名，值改为 `op://<vault-id>/<item-id>/<field-id>`。已确认开发、生产时使用不同文件与不同凭据；环境未知时只改当前本地入口。

通过仓库外的本机包装器执行 `op run --env-file=<本机私有引用文件> -- <原启动命令>`；项目命令及仓库脚本只消费通用环境变量。直接把 `op://` 字符串写到普通 dotenv 文件并不能自动解析。读取源码或当前框架文档，确认 dotenv、父进程环境、容器插值及启动参数的优先级；保留非敏感变量，避免原配置再次覆盖已注入的值。

用同一个入口执行注入检查：

```sh
op run --env-file=<本机私有引用文件> -- python /技能绝对路径/scripts/verify_env.py API_KEY DB_PASSWORD
```

执行时按项目 Python 环境替换上述示例命令；再运行项目自己的配置加载检查和最小只读功能验证。

## JSON、YAML、TOML 或固定文件消费者

消费者支持环境变量或凭据提供器时，优先使用其原生方式。仅在仓库外的本机配置中保存 `op://`，由本机工具解析后传给消费者；项目内仅保留通用配置字段、类型和加载合同。

必须接收明文文件时，使用引用模板并在启动时解析。`op inject` 输出真实凭据，必须直接交给子进程或受控的私有文件，不能返回到工具输出。只有消费方式确实需要文件时才创建权限 0600 的临时结果，设置清理及异常退出处理，并检查消费程序真的读取该文件。对普通密码，本次工作不另写持久明文副本；应用必须持久保存的私钥等作为明确的例外记录。模板 JSON/TOML 中的引用替换也可能破坏转义，应解析检查最终格式而非直接字符串拼接。

## Docker 与无人值守入口

核对 Compose 的插值来源、`environment`、`env_file` 及容器内应用加载顺序。`op run` 的宿主进程环境不保证自动传入容器；按实际变量逐个接入，避免把明文写进镜像构建参数或镜像层。静态检查可捕获解析结果后仅输出字段状态，不能直接显示展开后的 Compose 配置。

本地交互式桌面授权适用于开发启动。CI、计划任务、服务器和生产服务需要适合无人值守的认证方式；使用部署平台已有凭据管理系统，不引入 1Password Service Account 或其他本机工具依赖。保留已在 GitHub Secrets 等系统中运行的方案，不能靠本地验证宣称 CI 已迁移。

## 验证与恢复

入库、运行配置接入和功能验证是三个独立状态。重新读取比较已保存的值，只返回布尔结果；检查子进程看到的变量已解析；最后验证应用实际用该凭据完成最小功能。私钥验证文件权限和对应公钥，数据库验证只读连接，订阅验证加载结果；避免显示口令或非公开订阅地址。

回退仅恢复本次改动的字段和入口，保留并发或用户的其他修改。保留已创建条目的 ID、状态及用途映射；未验证成功的条目不标记为已接入。历史泄露与服务端密钥失效另列处理。
