# User Doctor

以用户原话和实际交付为依据，找出理解偏差、执行遗漏和重复返工的原因，给出可以核验的修正。诊断对象是需求理解、工作过程和结果，不是用户的人格或心理状态。

## 从用户的详细内容开始

根据当前请求确定检查范围：当前任务、指定项目或明确的历史时间段。先核对已有材料，只有缺失信息会实质改变结论时才询问。历史复盘使用明确日期；未指定窗口时可按最近 30 天并说明范围。

按顺序阅读范围内的用户消息及相关回复，追踪初始目标、补充条件、逐条批注、否定意见、纠正和最终确认。标题、索引、摘要用于定位；涉及细节的判断回到原文。用户要求完整阅读时，必须读取全部范围内正文；分页、截断和附件缺失分别列出，不能用抽样或批量提取替代。

建立足以覆盖请求的对应关系：用户要求及出处 → 当前有效含义 → 实际执行或交付 → 缺口与下一步。简单任务直接说明，复杂任务才使用表格或独立记录。核对以下细节：

- 目标项目、产品与数据来源；同名目录或相似任务不能相互替代。
- 用户指定的数值、口径、格式、模板、编辑能力、保存位置和验收方式。
- 必须保留、明确不要、只解释不修改、禁止委派等范围与操作限制。
- 后续纠正覆盖了哪些早期要求；未受影响的已确认要求继续有效。
- 用户真正确认的选择与助手自己的建议；沉默、重复建议和历史存在均不代表用户接受。

## 对照实际结果定位问题

以文件、当前配置、实际输出或有效验证记录判断落实状态。助手声称已完成、文件已生成、测试已启动，都不能单独证明交付满足要求。把已完成、部分完成、尚未开始、失败、待验证和无法访问分开表达。

每个重要问题说明：原要求是什么、实际发生了什么、差异给用户带来什么影响、证据在哪里、如何修正与验收。优先找出造成错误交付或反复纠正的原因；不要把一次事件扩大为用户长期特征，也不要把助手误解归因于用户能力不足。

涉及产品重构、替换入口或目录迁移时，同时核对旧能力在新实现中的位置、关键输入输出、保存与恢复、历史数据和导出。项目外关联的 PRD、ADR、测试和被忽略的数据也属于受影响范围。用户明确要求移除的能力单独记录；代码存在或构建通过不能单独证明能力等价。

## 从历史中提炼长期改进

需要跨任务复盘、工作方向分析或推荐 Skills、Hooks、Automations 时，阅读 [历史复盘与资产选择](references/history-review.md)。把用户的目标、实际投入、重复纠正与结果连起来，区分任务特有要求和得到多次证据支持的长期需求。

检查已有资产的实际内容、启用状态和作用范围，再判断是修订已有资产、增加一个窄范围能力，还是只修正当前任务。一次性问题不必包装成 Skill；可自动检测的稳定事件才考虑 Hook。

## 交付与修正

先回答用户最关心的缺口和影响，再给出证据及具体调整。按问题重要程度组织，格式适应任务，不强制固定数量、评分或整套模板。

检查或复盘请求默认交付建议；已有授权包含修正时，完成范围内的修改，不因内部审查结束而停止。新增外部操作或超出范围的变更按当前授权处理。遵循当前任务的委派、浏览器和测试限制，Skill 本身不增加权限。

历史审计报告说明已索引、已取得、完整阅读、部分阅读和不可取得的覆盖范围；重复副本不能当作独立事件。结论区分事实、推断和证据缺口，预计收益与实际观察到的收益分开。引用足够定位的日期、任务或文件，交付物不夹带密钥或无关私人原文。
