# Diagnose

1. 绑定 workflow、run、step 与执行环境，找到最后一次有证据的进展。先读调度状态、最近失败摘要和退出码。
2. 使用现有采集器；需要通用采集时读 contract 并调用 collect。按任务 ID、时间窗和读取预算缩小范围，分享日志前检查脱敏片段。
3. 根据证据选择一个最有辨别力、成本最低的假设进行验证。涉及多轮失败或成本异常时，使用已有历史查询或 contract 中的 audit；对照相同数据窗口、配置/脚本版本及用量口径。优先检查是否同因重复，而不是逐轮重做完整诊断。
4. 原因确定后最小修改，进入 validate 复测受影响步骤，再从一致的断点恢复。

| 现象 | 先检查 |
|---|---|
| 漏跑、迟到、重复启动 | 时区、启用状态、队列、上轮结束时间 |
| 进程存活而日志静默 | 最后工具调用、心跳、超时组件、锁持有者 |
| 每轮相同权限或依赖错误 | 目标执行器的命令、凭据引用、连接器与网络 |
| 重试后重复产物或发送 | 幂等键、回执、提交与保存状态的顺序；先对账 |
| 耗时或 Token 激增 | 阶段耗时、输入体积、重复读取及无效分支 |
| 成功状态与产物矛盾 | 业务验收规则、实际产物和交付回执 |
| 恢复后漏处理 | 游标、新鲜度、代码/配置版本、缓存键 |
| 多任务同时异常 | 共享配额、锁、上游任务、调度器与公共依赖，定位共同故障点 |
| 更新后才失败 | 变更前后版本、执行入口、环境差异；必要时按授权回滚并验证 |

区分已证实原因、待验证假设和缺失证据。缺少新事件时，检查心跳、进程或调度器状态，确认任务是否卡死。修复前保留相关失败记录与版本；已确定的检测或修复动作固化到现有脚本，并新增能复现该故障的回归检查。

遵守项目诊断预算；未配置时最多进行两轮有新证据的假设验证。同因失败且无新证据时停止该循环，返回待补证据与恢复条件。

**结束条件**：修复已通过相关验证，或达到预算并给出可执行的阻塞说明。回复失败步骤、证据、原因、修改、验证、恢复点及受影响紧后任务。
